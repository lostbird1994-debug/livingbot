# 文档处理

> 方法说明：本方法按既有办公/创作技能规范改写（规范改编），工具契约以本插件注册的原生工具为准。


先读取用户选中的原件和相关批注，沿用原格式。通过当前实际可用的文档工具处理
Word/PDF；没有相应工具时明确说明限制，不能把纯文本改扩展名伪装成文档。
普通文本使用原生文件工具即可，不为一次修改搭建文档系统。

修改前将批注定位到标题、段落、原文或页码。原文重复或定位不唯一时结合相邻
内容确定位置；仍有歧义才询问。针对选定内容做最小修改，保留其他章节、格式、
引用和用户已有改动。写入前重新核对当前原文；发现源文件已变化时重新定位，
不要覆盖新内容，也不要盲目重复已完成的修改。

默认在 tasks/<task>/ 或已有 projects/<project>/ 中创建修订副本，原件保持可读。
纯文本修订直接调用 livingbot_revise_document：一次只改一段，锚点照抄当前原文，
改了哪段、新版本的摘要和文件名都在返回里；原件不动，新版本单独交付，同一处锚点
重复出现会被拒绝而不是猜位置。需要连改多处就改新版本，不要在原文上叠加。
用户明确要求原位修改时沿用其选择，先保留原稿副本。逐条核对修改范围和批注
落实情况，交付时简述已改与未改之处，并说明这是第几个版本；生成文件后调用
livingbot_deliver_file。不要把解释、预览或输出路径当作已经交付的文件。

## 处理路径

先分清这是哪一种工作：只想看内容（预览、解释、摘要）就不要改文件；要改已有文件就走
精确修订；要新建才从头写。预览和查看不是内容工作，不因为“用户打开了文件”就顺手重写。
文本类交付默认保持原扩展名；工具只能产出 Markdown 时说明实际格式，不把 .md 改名成
.docx 冒充 Word 文件。只读格式（如没有编辑工具的 PDF）明确说明只能读，不尝试用打印或
转换脚本伪造可编辑结果。

## 本机工具边界

本方法能用的工具是 `livingbot_revise_document`（唯一文本锚点替换）与 `livingbot_deliver_file`（交付真实文件），
以及文件读取。**没有** WorkBuddy 平台的块级编辑、批注面板或 Office 编辑器；
需要它们时说明本机暂不支持，不把 Markdown 改名成 .docx 冒充 Word。

## 输入检查

动笔前确认四件事：源文件在哪、要交付什么格式、哪些内容必须原样保留、谁最终读它。
源文件先读一遍再改；读不到就说明原因，不要凭记忆编造原文。
用户给的是话题而不是资料时，先写出你要用的结构和大纲，再动内容。

## 步骤

1. 定位：按标题或唯一句子找到要改的位置，记下所在章节，避免在多处同名文本上误改。
2. 修改：只改需要改的段落；锚点必须唯一，出现多次时先扩大锚点再改。
3. 复核：改完重读受影响章节，确认没有断裂的编号、重复段落、丢失的表格或链接。
4. 交付：保存为新的文件名，用 livingbot_deliver_file 交付真实文件，并在回复里说清改了哪几处。

## 交付格式

- 正文用 Markdown；需要 Word/PDF 等格式时说明转换方式与已知差异。
- 保留原有标题层级、编号、表格列和脚注；不要顺手“美化”用户没要求的部分。
- 大改动用“改动清单”列出章节级别的前后差异，不贴全文。

## 边界

- 不整篇重写只为一处修改；不删除用户的原有段落来“让文章更顺”。
- 修改既有文件时保留原文件，输出用新名字。
- 无法确认事实的数字、引用和结论标为待确认，不自行补齐。
- 写入后重新读回受影响的段落再报告完成；只凭写入调用成功不算核对过。
